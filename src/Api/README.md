# API architecture

The API uses FastEndpoints and the Request–Endpoint–Response pattern. Each HTTP operation has a folder under `Homelab.Api/Features` containing its `Endpoint.cs`, `Request.cs` when it accepts input, and operation-specific response contracts. Endpoints use constructor injection and execute their own application workflow; there is no controller, mediator, generic repository, or route-registration layer between a slice and EF Core.

Related operations and their shared concepts stay together. For example, `Storage/Datasets` owns dataset inventory and rename reviews, `Storage/Pools` owns pool evidence and history, and `Hardware/Readings` owns manual reading validation and persistence. Reused contracts, entities, policies, and commands live at the nearest feature ancestor that needs them. Contracts used by one operation live inside that operation's folder. A slice can reuse a feature response type directly rather than introduce a duplicate response wrapper.

`Infrastructure` contains application-wide concerns: hosting, security, OpenAPI configuration, persistence, and migrations. `Program.cs` only composes the host. The shared EF context necessarily spans features. Existing entity namespaces remain `Homelab.Api` to preserve EF model identities, existing migration snapshots, and source compatibility with domain consumers; endpoint namespaces follow their feature folders. No schema migration or data conversion is required by this refactor.

## Contract and security

The existing `/api/v1` URLs, JSON shapes, cookie sessions, owner setup, rate limits, and read-only NAS behavior are preserved. `[FromBody]` on a request property keeps an existing JSON body at the root while route/query inputs stay separate. Domain validation retains existing error messages and conflict rules. Slice validators reject null bodies before a handler runs, and framework binding/validation errors use the existing `{ "error": "..." }` response shape.

Mutations still require `X-Homelab-Request: 1`. Database mutations are serialized through `WriteCoordinator`. Operations that perform network calls and acquire their own short leases declare `OwnsWriteLease` metadata, so the global middleware does not hold a writer lease during network waits. New endpoints require authentication unless they explicitly call `AllowAnonymous()`.

## OpenAPI, Scalar, and NSwag

Run the API in Development, either through Aspire or directly:

```sh
dotnet run --project src/Api/Homelab.Api
```

- `/openapi/v1.json`: one OpenAPI 3.0 document, generated by `FastEndpoints.OpenApi` using `Microsoft.AspNetCore.OpenApi` and Microsoft's `Microsoft.OpenApi` model. The 3.0 format keeps NSwag client generation interoperable.
- `/scalar/v1`: interactive Scalar reference, including cookie authentication, mutation headers, input schemas, feature tags, and success/error responses. Sign in through the login operation; the browser sends the resulting HttpOnly cookie.
- These documentation endpoints are mapped only in Development.

NSwag consumes the same document; it does not run a second server-side schema generator. From `src/Api`, with the Development API running:

```sh
dotnet tool restore
dotnet nswag run nswag.json /variables:ApiUrl=http://127.0.0.1:5253
```

The API address can be changed with `ApiUrl`. The generated C# client goes to the ignored `artifacts/clients` directory by default. Supply a configured `HttpClient` with its base address, cookie handling, and the required mutation header. Generated clients are optional and do not replace the existing web application's contracts.

## Logging and telemetry

`Homelab.ServiceDefaults` configures UTC console logs with structured scopes and OpenTelemetry logs, ASP.NET Core/HTTP traces, and runtime/request metrics. API completion logs contain method, route template, status, and duration; they omit request bodies, headers, query strings, and concrete route values.

When Aspire starts the API, it supplies the OTLP endpoint and resource configuration and receives logs, traces, and metrics directly in its dashboard. A separate collector is not required for this stack. Standalone operation continues to log to the console. To export to an external collector, set `OTEL_EXPORTER_OTLP_ENDPOINT` and the matching `OTEL_EXPORTER_OTLP_PROTOCOL` (`grpc` or `http/protobuf`), plus headers if the receiver requires authentication. Export is enabled only when an OTLP endpoint is configured; standard OpenTelemetry environment settings control batching and resource attributes.

## Validation

```sh
dotnet build src/Api/Homelab.sln
dotnet test src/Api/Tests/Homelab.Tests
dotnet ef migrations has-pending-model-changes --project src/Api/Homelab.Api
```

`ApiArchitectureTests` checks the pre-refactor method/route inventory, authorization metadata, JSON body binding, mutation guards, OpenAPI operation coverage and parameter sources, Scalar, and both logging providers. Existing integration and domain tests cover persisted evidence, concurrency, recovery revisions, hardware operations, credentials, and transport restrictions.

## Integration providers

`ApiHosting` registers built-in providers by stable ID. The existing NAS connection flow selects `truenas`, and Synology hardware collection resolves `synology` from the server platform. The registry rejects unknown IDs and incompatible capabilities. Both settings flows continue to use their current routes and stored credentials.

To add a storage integration, implement the storage provider and read session, register it, and wire its settings flow to select its ID. Translate remote responses at the provider boundary into the app's inventory, alert, hardware, and evidence inputs. Preserve the distinction between a successful empty read, unsupported data, and a failed read. Add transport and response translation fixtures for the new provider. Keep remote operations read-only and use explicit allowlists where the transport accepts method names.

Workers own scheduling, configuration revision checks, and evidence persistence. Hardware sources share detected components and collected readings while retaining their own acquisition and timing rules. Extend an existing capability when the data has the same meaning. Add a separate capability when the device reports a different kind of evidence.
